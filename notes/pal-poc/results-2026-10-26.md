# sid PAL PoC 후속 측정 결과 (2026-10-26)

- 측정 호스트: sid (Xeon Ice Lake-SP 2소켓, NVIDIA L4, 드라이버 580.178.04)
- 커널: `7.0.0-rc1-pal+`, NVIDIA exporter와 upcie importer 이식본
- 절차: `MANUAL-followup.md` 1~10절. sia의 Claude Code 세션이 실행했고 운영자가 단계마다 승인했다.
- 원본 로그: `sid-raw/followup-2026-10-26/`
- 시험 장치(운영자 선택): 기준 `0000:4e:00.0`(소켓 0, 호스트 브리지 4a), 같은 소켓 다른 스택 `0000:67:00.0`(소켓 0, 호스트 브리지 64), 다른 소켓 `0000:cc:00.0`(소켓 1, 호스트 브리지 c9). 세 장치 모두 SLBA 0이고, 쓰기 측정은 1 GiB를 덮어썼다. 데이터셋 장치 `0000:4d:00.0`은 어떤 명령에도 넣지 않았다.

## 요약

**질문.** 1차 측정(`results-2026-10-15.md`)은 PAL 경로가 sid에서 양방향으로 동작함을 보였다. 이번 측정은 남은 세 질문에 답한다. PAL 경로가 지금 쓰는 `iommu_map_pa` 경로보다 느린가, 다른 IIO 스택과 다른 소켓의 NVMe에서도 동작하는가, fd close와 `cuMemFree`와 강제 종료에서 매핑과 GPU 메모리가 안전하게 정리되는가.

**답.** PAL 경로는 `iommu_map_pa`보다 느리지 않다. 1 GiB 매핑 비용은 PAL이 약 8배 낮다. 세 경로 모두 C1과 C2가 데이터 일치했고, 수명 시나리오 세 가지에서 GPU 메모리가 안전하게 정리됐다.

**이유.** 두 경로는 모두 2 MiB IOMMU 페이지로 같은 BAR1 주소를 매핑하므로, 매핑 뒤의 DMA 경로가 같다. 매핑 비용의 차이는 `iommu_map_pa`가 2 MiB마다 `iommu_map()`을 따로 부르는 구조와 맞는다. 수명 시나리오에서는 iommufd와 `iommu_map_pa`가 모두 dma-buf 참조를 쥐고 있어서, NVIDIA가 매핑이 풀릴 때까지 메모리를 해제하지 않았다.

**성립 조건.** 측정한 서버는 sid 한 대다. GPU는 L4 한 장(호스트 브리지 30)이고, NVMe는 Samsung MZTLD15THEPB 세 대로 모두 Microchip 스위치 아래에 있다. 처리량은 큐 하나, 순차 접근, 1 GiB 구간에서 쟀다.

**측정값.**

| 항목 | PAL | `iommu_map_pa` | host 대상 |
| --- | --- | --- | --- |
| wr 128K qd32 (MB/s, 기준 장치) | 6423.7 | 6424.4 | 6424.3 |
| rd 128K qd32 (MB/s, 기준 장치 1회차) | 6588.6 | 6367.0 | 6547.5 |
| rd 4K qd1, 읽기만 한 3회 (MB/s) | 639.4~639.8 | 637.6~637.9 | 639.0~639.6 |
| 1 GiB 매핑 p50 / p99 (µs) | 4.1 / 4.4 | 33.5 / 35.7 | 해당 없음 |
| 1 GiB 해제 p50 / p99 (µs) | 3.1 / 3.6 | 2.5 / 2.9 | 해당 없음 |
| C1, C2 (4e, 67, cc) | 모두 MATCH | 모두 MATCH | 해당 없음 |
| `cuMemFree` 직후 / unmap 뒤 CUDA 여유 메모리 (MiB) | 21345 / 22369 | 21345 / 22369 | 해당 없음 |

**의미.** 성능, 경로, 수명의 세 측면 모두에서 `iommu_map_pa`를 PAL 경로로 대체하지 못할 이유가 측정되지 않았다. 소켓을 건너는 UPI 경로에서도 GPU → NVMe P2P가 동작했다. 이로써 1차 보고서가 남긴 "같은 소켓 안의 경로 하나"라는 한계가 줄었다.

**바로잡은 이전 기록.** sid 세션의 첫 보고는 rd 128K qd32에서 PAL이 3~4.5% 높다고 적었고, rd 4K qd1의 1회차 차이(6.1%)는 이상치로 보았다. 이 차이는 측정 순서에서 생겼을 가능성이 크다. PAL이 더 빠르다고 결론 내리지 않는다(§4.3).

**확인하지 못한 것.** rd 128K qd32 차이가 측정 순서 효과인지는 읽기만 한 반복 측정으로 확인해야 한다(`MANUAL-followup.md` 11절). 여러 큐, 임의 접근, 여러 GPU는 측정하지 않았다(§7).

**반영한 변경.** `followup-run.sh`의 bench 순서를 구간 채우기, 모든 경로의 읽기, 모든 경로의 쓰기 순서로 바꿨다. 경로 순서는 `ORDER`로 바꿀 수 있다.

## 1. 측정 구성

`pal_nvme`는 vfio cdev와 iommufd 위에서 동작하는 최소 NVMe 드라이버다. 이번 측정은 같은 드라이버 코드에서 GPU 매핑 방식만 바꿨다. PAL 경로는 `IOMMU_IOAS_MAP_FILE`로 CUDA dma-buf를 매핑한다. `iommu_map_pa` 경로(`--map-pa`)는 `dmabuf_import`로 BAR1 물리주소를 얻은 뒤, `iommu_map_pa` 모듈로 IOVA 256 GiB에 2 MiB 페이지로 매핑한다. 이 조건은 xNVMe가 쓰는 조건과 같다. host 대상(`--target host`)은 NVMe와 같은 iommufd IOAS에 매핑한 호스트 메모리 6 MiB이고, P2P가 없는 기준선으로 쓴다.

세 장치의 sysfs 경로는 다음과 같다(`f-E-4e.txt`, `f-G-bench-*.txt`의 `== path` 줄).

| 장치 | 경로 | NUMA |
| --- | --- | --- |
| `4e:00.0` | `pci0000:4a/4a:02.0/4b:00.0/4c:01.0/4e:00.0` | 0 |
| `67:00.0` | `pci0000:64/64:02.0/65:00.0/66:00.0/67:00.0` | 0 |
| `cc:00.0` | `pci0000:c9/c9:02.0/ca:00.0/cb:00.0/cc:00.0` | 1 |

GPU는 `pci0000:30/30:02.0/31:00.0`(소켓 0)에 있다. 따라서 `cc:00.0`과 GPU 사이의 P2P는 소켓 사이의 UPI를 지난다. 세 NVMe의 MDTS는 256 KiB이므로 128 KiB 전송은 한 명령으로 나간다.

## 2. 정합성과 경로

세 장치에서 `followup-run.sh <BDF> 0 c`를 실행했다. 각 장치에서 PAL 64K, PAL 4K, `--map-pa` 64K를 시험했다.

| 경로 | C1 (NVMe → GPU) | C2 (GPU → NVMe) | D (미매핑 IOVA) | DevSta, UESta |
| --- | --- | --- | --- | --- |
| 소켓 0, 스택 4a → 30 (`4e`) | MATCH | MATCH | `sc=0x4` | 오류 없음 |
| 소켓 0, 스택 64 → 30 (`67`) | MATCH | MATCH | `sc=0x4` | 오류 없음 |
| 소켓 1 → 소켓 0 스택 30 (`cc`) | MATCH | MATCH | `sc=0x4` | 오류 없음 |

세 경로 모두 두 매핑 방식에서 양방향 데이터가 일치했다. 미매핑 IOVA로 보낸 명령만 `sc=0x4`로 실패했다. `CmpltTO`, `UnsupReq` 같은 오류 비트는 서지 않았다. 매뉴얼은 소켓 사이 P2P를 Intel이 지원하는지 확인하지 못했다고 적었는데, 이 경로가 sid에서 동작함을 실측으로 확인했다.

## 3. 매핑 비용

`--map-loop 1000`은 1 GiB 매핑을 1000번 해제하고 다시 매핑하며, 각 ioctl의 지연을 사용자 공간에서 잰다. 두 번 실행했다.

| 실행 | PAL map p50 / p99 | map-pa map p50 / p99 | PAL unmap p50 / p99 | map-pa unmap p50 / p99 |
| --- | --- | --- | --- | --- |
| 1회차 (`f-E-4e.txt`) | 4.1 / 4.4 | 33.5 / 35.7 | 3.1 / 3.6 | 2.5 / 2.9 |
| 재실행 (`f-E-4e-rerun.txt`) | 4.1 / 4.9 | 33.5 / 35.8 | 3.5 / 4.0 | 2.8 / 3.4 |

단위는 µs다. 매핑은 PAL이 약 8배 빠르고, 해제는 두 경로가 비슷하다. 두 실행의 값이 거의 같아서 재현성이 있다. 개발 PC에서도 같은 경향이었다(PAL 4.9 µs, map-pa 82.8 µs). map-pa의 PA 조회(`dmabuf_import`)는 루프 밖에서 한 번만 하므로, map-pa 값은 `iommu_map_pa` ioctl만의 비용이다. 실제 xNVMe 흐름은 이 조회 비용을 더 낸다.

## 4. 처리량

### 4.1 측정 순서

당시 `followup-run.sh`의 bench 부분은 다음 순서로 실행했다. 경로마다 qd1 4K와 qd32 128K를 10초씩 잰다.

| 순서 | 측정 | 직전에 일어난 일 |
| --- | --- | --- |
| 1, 2 | PAL rd | 정합성 시험(쓰기 384섹터) |
| 3, 4 | PAL wr | PAL rd |
| 5, 6 | map-pa rd | PAL wr 128K qd32 (10초, 약 64 GB) |
| 7, 8 | map-pa wr | map-pa rd |
| 9, 10 | host rd | map-pa wr 128K qd32 |
| 11, 12 | host wr | host rd |

이 순서에서는 PAL 읽기만 쓰기 부하가 없는 상태에서 측정되고, map-pa와 host 읽기는 대량 쓰기 직후에 측정된다. SSD는 쓰기 뒤에도 내부 정리 작업을 계속할 수 있고, 그동안 읽기 지연이 늘어날 수 있다. 이 순서는 매뉴얼을 쓸 때 고려하지 못한 점이다.

### 4.3 해석

sid 세션의 첫 보고는 이 결과를 다음과 같이 해석했고, 이 문서는 그 해석을 고친다.

| 항목 | 첫 보고 | 고친 해석 |
| --- | --- | --- |
| rd 128K qd32 | PAL이 map-pa보다 일관되게 3~4.5% 높다 | PAL 값만 쓰기 부하 없이 측정됐다. 원인은 확정하지 않는다 |
| rd 4K qd1 1회차 6.1% 차이 | 재현되지 않은 이상치 | 측정 순서 효과다. 67과 cc에서도 같은 차이가 나왔다 |

첫 보고는 4e의 재실행과 추가 측정만 1회차와 비교했다. 그래서 67과 cc의 bench 로그에서도 같은 차이(PAL 718.7, 718.8 대 map-pa 674.6, 676.7)가 반복된 것을 놓쳤다.

쓰기는 세 대상과 세 경로에서 6424 MB/s로 같다. 이 값은 NVMe의 순차 쓰기 한계로 추정한다. 쓰기 방향은 장치가 GPU BAR1을 읽는 P2P인데, 이 방향이 host 메모리를 읽는 경우와 같은 처리량을 냈다.

읽기에서 PAL이 높게 나온 값은 모두 4.1절의 순서에서 쓰기 부하 없이 측정된 값이다. 다음 세 관측이 측정 순서 효과를 가리킨다.

| 관측 | 측정 순서 효과라면 예상되는 것 | 측정값 |
| --- | --- | --- |
| rd 128K qd32 p99 | 쓰기 직후 읽기(map-pa, host)만 p99가 높다 | PAL 636 µs (재실행 제외), map-pa와 host 879~930 µs |
| rd 4K qd1, 쓰기가 낀 실행 | PAL만 높다 | PAL 718.7~718.9, map-pa와 host 674.6~679.3 |
| rd 4K qd1, 읽기만 한 실행 | 세 경로가 같다 | 637.6~639.8, 차이 0.3% 이내 |

4K qd1의 차이는 읽기만 한 측정에서 사라졌으므로, 측정 순서에서 생긴 것으로 판단한다. 128K qd32에서도 PAL 우위(3.1~4.5%)는 쓰기 부하가 없던 측정과 쓰기 직후 측정을 비교한 값이다. 그래서 순서 효과일 가능성이 크다. 다만 4e 재실행에서는 PAL 읽기도 직전 실행의 쓰기 뒤에 측정됐는데 6588.0 MB/s를 유지했고, p99만 1130.3 µs로 올랐다. 이 관측은 순서 효과만으로 다 설명되지 않는다. 그래서 128K 차이의 원인은 확정하지 않는다. 확정하려면 `MANUAL-followup.md` 11절처럼 읽기만 하면서 경로 순서를 바꿔 반복한다.

1회차와 4e 재실행 사이에 4K qd1 값이 719에서 639로 내려간 것도 장치 상태 때문으로 추정한다. 1회차의 PAL 읽기는 대부분 아직 쓰지 않은 LBA를 읽었다. 개발 PC에서도 방금 쓴 1 MiB를 읽는 4K qd1이 148 MB/s로, 1 GiB 구간의 623 MB/s보다 크게 낮았다(`devpc-raw/order-test-2026-10-26.log`). LBA 상태가 읽기 성능을 크게 바꾼다는 뜻이다.

경로별로 보면 PAL 값은 세 장치에서 같았다(rd 128K qd32 6588.3~6588.6, wr 6423.7~6424.3 MB/s). 다른 스택과 다른 소켓에서 처리량 저하는 측정되지 않았다.

## 5. 수명 시나리오

기준 장치에서 `followup-run.sh 0000:4e:00.0 0 life`를 실행했다(`f-H-4e.txt`).

| 시험 | 확인하는 것 | 결과 |
| --- | --- | --- |
| close (PAL) | fd를 닫아도 매핑이 유지되는가 | C1, C2 MATCH. unmap과 close 뒤 여유 메모리 22369 MiB |
| close (map-pa) | 같다 | C1, C2 MATCH. 22369 MiB |
| free: `cuMemFree` 직후 | 매핑이 남아 있으면 NVIDIA가 메모리를 해제하는가 | 해제 전후 모두 21345 MiB. 해제하지 않았다 |
| free: F1 | 옛 IOVA로 쓴 데이터가 새 버퍼를 덮어쓰는가 | intact. 옛 버퍼 PA `0x20a031e00000`, 새 버퍼 PA `0x20a071e00000` |
| free: F2 | 옛 IOVA가 아직 옛 메모리를 가리키는가 | yes |
| free: unmap 뒤 | 매핑을 풀면 메모리가 돌아오는가 | 21345 → 22369 MiB (1 GiB 반환) |
| kill -9 | 읽기 측정 중 강제 종료 뒤 정리되는가 | 다음 실행 C1, C2 MATCH. GPU 사용 메모리 0 MiB. dmesg 비어 있음 |

PAL과 map-pa의 결과는 같았다. map-pa도 `IOMMU_MAP_PA` 요청에 dma-buf fd를 넘겨 참조를 쥐기 때문이다. `cuMemFree` 뒤 메모리가 해제되지 않고 F2가 yes이므로, NVIDIA는 dma-buf 참조가 남아 있는 동안 메모리를 다른 할당에 내주지 않는다. 그래서 살아 있는 매핑이 해제된 메모리를 통해 다른 버퍼를 덮어쓰는 일은 일어나지 않았다. 대신 응용이 `cuMemFree`를 불러도 매핑을 풀기 전까지 GPU 메모리가 돌아오지 않는다. NVIDIA exporter는 `dma_buf_invalidate_mappings()`를 부르지 않으므로(`REPORT.md` §10), 메모리 반환 시점은 importer가 정한다. 개발 PC에서는 F2를 측정하지 못했는데, sid에서 측정해 이 결론을 확정했다.

dmesg에는 `BUG`, `WARNING`, `DMAR`, `AER`, `NVRM` 줄이 없었다.

## 6. 원상 복구

- 기본 커널 `7.0.0-38-generic`로 재부팅했다. NVIDIA L4 580.178.04는 정상이고, 세 장치 모두 nvme 드라이버로 돌아왔다(`f-recover3.txt`).
- GPU compute 프로세스는 0개이고, `/mnt/datasets`는 측정 전과 같이 마운트되어 있지 않다.
- PAL 부팅 직후 `next_entry`를 해제했다(`f-postboot.txt`의 grubenv가 비어 있다).
- `GRUB_DEFAULT`는 `7.0.0-38-generic` 항목으로 고정한 채 두었다. PAL 커널 파일과 `/root/pal-poc`도 남겼다. 둘 다 운영자가 결정했다.

| rd 128K qd32에서 PAL이 3.1~4.5% 높은 원인 | `MANUAL-followup.md` 11절: 읽기만, 경로 순서를 바꿔 4회 |
| 4K qd1 값이 실행마다 639와 719로 갈리는 원인 | 구간을 한 번 채우고 쉰 뒤 측정하는 새 bench 순서로 다시 잰다 |
| 여러 큐, 임의 접근, 큰 구간에서의 차이 | xNVMe의 PAL 백엔드를 만든 뒤 fio로 잰다 |
| xNVMe 흐름 전체의 매핑 비용 (PA 조회 포함) | xNVMe에서 `dmamem_from_cuda_iommu_map_pa()` 전체를 잰다 |
| 다른 GPU 위치(소켓 1)와 여러 GPU | 다른 슬롯의 GPU가 있는 서버에서 같은 스크립트를 실행한다 |
| `cuMemFree` 뒤 GPU 메모리가 매핑 해제까지 남는 동작이 응용에 주는 영향 | xNVMe가 GPU 버퍼를 해제하기 전에 unmap하는지 코드에서 확인한다 |
