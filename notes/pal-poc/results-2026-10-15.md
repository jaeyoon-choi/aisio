## 0. 한 줄 결론

sid(Ice Lake-SP)에서 업스트림 Jason Gunthorpe PAL 브랜치 커널 + 이식한 NVIDIA exporter + upcie importer로, **NVMe가 CUDA GPU 메모리에 dma-buf로 DMA하는 경로가 번역(IOMMU) 유무와 무관하게, 양방향(NVMe→GPU, GPU→NVMe) 모두 성공**했다. 개발 PC에서 유일하게 실패했던 방향(GPU→NVMe, 즉 장치가 GPU BAR1을 읽는 non-posted peer read)이 sid에서는 성공했으므로, **그 실패는 개발 PC의 클라이언트 루트 콤플렉스 제약이었고 PAL/iommufd 문제가 아님**이 대조로 확인됐다. → 자체 workaround 모듈 `iommu_map_pa`(`iommu_map(...,IOMMU_MMIO)`)를 업스트림 PAL `IOMMU_IOAS_MAP_FILE` 경로로 대체할 근거 확보.

## 1. 질문과 배경

본 팀은 NVMe가 CUDA로 할당한 GPU 메모리에 직접 DMA하도록 그 메모리를 NVMe의 IOMMU 페이지 테이블에 넣어야 한다. 현재는 자체 커널모듈 `iommu_map_pa`가 이 일을 한다. 업스트림 iommufd의 `IOMMU_IOAS_MAP_FILE`이 CUDA dma-buf를 받으면 그 모듈을 걷어낼 수 있는데, 업스트림엔 아직 그 기능이 없다. Jason Gunthorpe의 PAL(Physical Address List) RFC(`jgunthorpe/linux` `dmabuf_map_type` `c37cf2824740`)가 iommufd 쪽을 구현한다.

개발 PC(i9-14900K, 호스트 브리지 8086:a700)에서 확인한 결과:

| 확인한 것 | 결과 (dev PC) |
| --- | --- |
| CUDA dma-buf를 `IOMMU_IOAS_MAP_FILE`로 매핑 | 성공, 2 MiB 엔트리 512개 |
| NVMe → GPU (NVMe 읽기 명령 = 장치가 GPU에 씀, peer **posted write**) | 데이터 일치 |
| 매핑하지 않은 IOVA | DMAR fault + 명령 오류 |
| GPU → NVMe (NVMe 쓰기 명령 = 장치가 GPU BAR1을 읽음, peer **non-posted read**) | 실패 `sc=0x4`, 번역을 꺼도 실패, CPU는 같은 BAR1 정상 |

sid에서 답할 질문 두 개:
1. sid에서 번역 없이(untranslated) NVMe↔GPU P2P(특히 GPU→NVMe)가 되는가. (단계 A)
2. 된다면 PAL 경로(iommufd 번역)로도 C1/C2가 모두 되는가. (단계 B, C)

배경 사실 **[측정/문헌]**:
- 비-posted PCIe read(메모리를 읽는 요청)는 완료(completion)가 필요하므로 peer 라우팅 실패가 오류로 드러난다. posted write(메모리에 쓰는 요청)는 완료가 없어 실패가 드러나지 않는다. 그래서 "GPU→NVMe"만 원인을 가른다.
- 커널 `drivers/pci/p2pdma.c`의 P2P 허용목록: 개발 PC의 `8086:a700`은 없고 sid의 `8086:09a2`는 있다(로컬 6.8 소스에서 `{PCI_VENDOR_ID_INTEL, 0x09a2, 0}` 확인). 허용목록 `flags=0`은 **다른 host bridge(=다른 root complex) 사이도 허용**한다는 뜻(같은 소스의 `host_bridge_whitelist()`가 a≠b일 때 양쪽을 `same_host_bridge=false`로 검사). 옛 Xeon E5(`0x3c00/0x3c01`)는 `REQ_SAME_HOST_BRIDGE`라 same-RC만 허용 — 대비된다. 단 **우리 시험 경로(`iommu_map_pa`/PAL)는 p2pdma 판정을 거치지 않으므로 이 허용목록은 시험 성패를 정하지 않는다(간접 근거일 뿐)** [consult 지적, 코드 근거: upcie `experimental/iommu_map_pa/module/iommu_map_pa.c`가 `iommu_map(...,IOMMU_MMIO)` 직접 사용].

### 2.2 토폴로지 (P2P 관점)  **[측정]**
- GPU: `0000:31:00.0` → 루트포트 `0000:30:02.0` → **root complex `pci0000:30`**. 이 stack(30)의 엔드포인트는 GPU뿐 — **NVMe 없음**.
- NVMe 후보(socket0, node 0): RC `pci0000:4a`(`4e,4f,50,51,52,53,54` @ 루트포트 `4c:01..07`) 및 RC `pci0000:64`(`67..6e` @ `66:00..07`). RC `c9`,`e2`는 node1(socket1).
- **따라서 이 시험은 항상 cross-root-complex**(GPU RC 30 ↔ NVMe RC 4a). sid에서 same-RC 양성 대조는 불가(GPU stack에 NVMe가 없음). 이 사실은 결과 해석에 명시해야 한다.
- ACS **[측정]**: GPU 루트포트 `30:02.0`과 후보 루트포트 `4c:01.0` 모두 `ACSCtl: TransBlk-` → 이 루트포트들에서 P2P가 ACS로 차단되지 않음. (`raw/topology.txt`)
- `nvidia-smi topo -m`: GPU0 ↔ NIC0/NIC1 = `SYS`(UPI 경유). NVMe는 topo에 안 나옴. (`raw/nvidia.txt`)

### 4.3 하네스 결함과 수정 (승인 후)  **[측정]**
첫 시도에서 A1이 C1/C2 도달 전 `create io cq failed: 0x102`로 실패. 원인은 시험 하네스 `pal_nvme.c`가 CC의 IOSQES/IOCQES를 뒤바꿔 쓴 것. 커널 헤더(`IOSQES_SHIFT=16`, `IOCQES_SHIFT=20`, `NVME_NVM_IOSQES=6`, `NVME_NVM_IOCQES=4`) 기준:
```
- wr32(c, 0x14, (6 << 20) | (4 << 16) | 1);   # 실제 0x00640001 → IOSQES=4, IOCQES=6 (스왑)
+ wr32(c, 0x14, (6 << 16) | (4 << 20) | 1);   # 0x00460001 → IOSQES=6, IOCQES=4 (올바름)
```
admin queue는 엔트리 크기가 64B/16B 고정이라 CC와 무관 → Identify까지 성공. I/O CQ 생성은 CC.IOCQES=6(CQ 엔트리 64B)이라 sid 엔터프라이즈 드라이브가 `Invalid Queue Size`(`0x102`=NVME_SC_QUEUE_SIZE)로 거부. 개발 PC 소비자급 드라이브는 관용. (diff: `raw/pal_nvme-cc-fix.diff`)

## 5. 해석 (측정 vs 추정)  **[측정]**
- **C2가 sid에서 MATCH**: 장치가 GPU BAR1을 읽는 non-posted peer read가 cross-RC(GPU RC 30 ↔ NVMe RC 4a, 같은 소켓/socket0)에서 성공. dev PC(same-RC)에서는 실패했던 방향. → **dev PC의 C2 실패는 클라이언트 루트 콤플렉스(8086:a700)의 P2P read 제약이었고, PAL/번역/iommufd 문제가 아님**을 대조로 확인.
- **단계 A와 C의 차이 없음**: sid에서는 번역 없이(identity+uio)도, PAL 번역(iommufd)으로도 방향 제약 없이 C1/C2가 됨. 즉 이 플랫폼에서는 번역 유무가 P2P 성립을 가르지 않는다.
- **SNP는 원인 아님**: SNP가 켜진 PTE(`0x…883`)에서도 C2가 성공(dev PC에서도 SNP를 끄고 실패 → SNP 무관 확정). `patches/kernel-vtdss-mmio-nosnp.patch` 불필요.
- **측정 범위/조건**: 결과는 sid(Ice Lake-SP, VT-d, vfio-pci cdev + iommufd), NVIDIA 580.178.04 이식본, upcie 0.9.0 이식본, 1 GiB 단일 구간 CUDA 버퍼, 4 KiB/64 KiB 전송, cross-RC(socket0) 조건에 대한 것. same-RC 대조는 sid에서 불가(GPU stack에 NVMe가 없음) — 이 점 때문에 "same-RC면 된다/안 된다"는 결론은 이 실험이 답하지 않는다.
- **미확인**: exporter가 attach 시 자체 p2pdma 판정을 하는지(consult 미확인 항목), C2 성공의 대역폭/지연 특성(이번엔 데이터 일치만 확인).

## 6. 매뉴얼과의 편차 / 새로 알게 된 것 (모두 기록)

1. **접속**: 매뉴얼의 `ssh root@sid`(무비밀번호) 불가. `jaeyoon@sid`(비밀번호 인증) + `sudo`로 root. (`~/pal-poc-sid/params.env`)
2. **CUDA 13.3**(dev PC와 다름): sid `cuda.h`가 `cuCtxCreate`→`cuCtxCreate_v4(pctx, ctxCreateParams, flags, dev)`(4인자). 시험 소스는 3인자 → **`gcc -include sid-cuda13-compat.h` shim**으로 소스 무수정 빌드(규칙 5 준수). shim: `~/pal-poc-sid/sid-cuda13-compat.h`.
3. **하네스 버그**: `pal_nvme.c` CC IOSQES/IOCQES 스왑 → sid 드라이브가 Create I/O CQ를 `0x102`로 거부. 승인 후 1줄 수정(`raw/pal_nvme-cc-fix.diff`). 이 엔터프라이즈 드라이브(`MZTLD15THEPB`)가 CC 엔트리 크기를 검증하는 반면 dev PC 소비자급은 관용.
4. **`libdw-dev` 필요**: `scripts/gendwarfksyms`가 `<dwarf.h>` 요구(커널 7.0-rc1). 매뉴얼 사전 점검 목록엔 없었음. 승인 후 설치.
5. **커널 소스 취득**: sid/sia 프록시가 linux급 repo의 git 응답(대형 ref 광고)을 못 넘김(80초 0바이트). codeload/raw/api는 429. **github PAT의 Basic 인증(`https://x-access-token:<PAT>@github.com/...`)**으로 clone 성공. (`logs/stageB-net*.txt`, `stageB-clone*.txt`)
6. **initramfs dm 검사 오탐**: 매뉴얼은 initramfs에 `dm-mod|dm_mod`가 없으면 멈추라 하지만, sid는 `CONFIG_BLK_DEV_DM=y`(dm 내장)라 그 모듈이 존재하지 않음. **현재 부팅되는 34-generic의 initrd도 같은 grep으로 0** → 이 체계(dracut+내장dm)에서 검사가 무의미. `update-initramfs`(dracut 110)가 `overlayroot depends on overlayfs` 오류를 냈으나 initrd는 생성됨(LVM 지원 포함: `usr/sbin/lvm`, `dm-mirror/round-robin/multipath/log/region-hash`).
7. **GRUB 기본 항목 보호**: `7.0.0-rc1-pal+`가 버전정렬(dpkg/sort -V)상 최신이라 `update-grub` 시 기본이 PAL로 바뀔 수 있었음. `GRUB_DEFAULT=0`이었으므로 **`GRUB_DEFAULT`를 `"Advanced options for Ubuntu>Ubuntu, with Linux 7.0.0-38-generic"`으로 고정**해 기본 커널을 불변으로 유지. (매뉴얼 규칙 3)
8. **grub-reboot가 1회성이 아님**: sid는 `/boot/grub/grubenv`가 **LVM 위**라 GRUB이 쓸 수 없다(`grub-reboot` 스크립트가 `WARNING: Detected GRUB environment block on lvm device ... will remain the default boot entry until manually cleared`를 출력). 즉 `next_entry`가 부팅 후에도 지워지지 않는다 → 매뉴얼의 "전원 재투입 시 기본 커널 복귀" 안전망이 성립하지 않음. **원격 콘솔(BMC/IPMI)이 없어**, PAL 커널이 부팅 실패하면 원격 복귀가 불가. 이 위험은 재부팅 전에 운영자에게 보고·승인받았고, PAL 부팅 성공 직후 `grub-editenv /boot/grub/grubenv unset next_entry`로 해제했다.

## 9. 재현 요약 (다른 환경/사람이 다시 하려면)

1. `sid` 접속: `ssh jaeyoon@sid` + `sudo`. 시험 장치는 socket0의 NVMe(`0000:4d:00.0` 제외), `groupsize=1`. 데이터셋 `4d`는 절대 쓰지 않음.
2. 시험 소스는 `pal_probe`(CUDA 1 GiB dma-buf → `IOMMU_IOAS_MAP_FILE`), `pal_nvme`(vfio cdev+iommufd 최소 NVMe 드라이버) — 매뉴얼 `sid-bundle/src`.
3. 번역 없는 시험(단계 A): `identity-uio.sh`, `pal_nvme --uio`, `bar1_cpu_read`, `restore-nvme.sh`.
4. PAL 커널: `jgunthorpe/linux` `c37cf2824740`(git 인증 필요) → config(위 CONFIG_들) → `make -j` → `arch/x86/boot/bzImage`. NVIDIA 580.178.04에 `nvidia-580.178.04-pal-port.patch` 수동 빌드, upcie 0.9.0에 `upcie-experimental-0.9.0-pal-port.patch`.
5. 설치: `modules_install` + `extra/` .ko + `depkg -a` + `/boot` 복사 + `update-initramfs`. **GRUB 기본 고정** 후 `grub-reboot`로 1회 부팅(단, LVM grubenv면 next_entry가 안 지워지므로 부팅 후 수동 해제).
6. 번역 시험(단계 C): `bind-vfio.sh`, `pal_probe --vfio`, `pal_nvme --vfio --slba N [--xfer 4096] [--identity --no-negative]`, `pte-dump.sh`.
7. 복구: `restore-nvme.sh`, 기본 커널로 재부팅.
