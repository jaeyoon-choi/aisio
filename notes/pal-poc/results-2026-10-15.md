# PAL PoC 2차 결과: sid(Ice Lake-SP)에서의 NVMe와 GPU 간 양방향 DMA

- 측정일: 2026-10-14 ~ 2026-10-15
- 호스트: sid (Ice Lake-SP 2소켓, 호스트 브리지 8086:09a2, NVIDIA L4 at 0000:31:00.0, 시험 NVMe Samsung MZTLD15THEPB at 0000:4e:00.0)
- 커널: 단계 A는 배포 커널 `7.0.0-34-generic`, 단계 C는 `7.0.0-rc1-pal+` (PAL 브랜치 c37cf2824740), 모두 `intel_iommu=on`, passthrough 없음
- 드라이버와 도구: 개발 PC와 같은 이식 패치(`patches/`)와 시험 도구(`src/`), 절차는 `MANUAL.md`
- 실행: sia의 Claude Code 세션이 매뉴얼을 따라 실행했고, 운영자가 단계마다 승인했다. 원본 로그와 실행 스크립트는 `sid-raw/`에 있다. 이 문서의 숫자는 그 로그에서 직접 옮겼다.

## 요약

**질문.** 개발 PC에서 GPU→NVMe 방향(NVMe가 GPU BAR1을 읽는 쓰기 명령, C2)은 번역이 있든 없든 `sc=0x4`로 실패했다. sid에서는 번역 없이 C2가 되는가. 된다면 PAL 경로(iommufd 번역)로도 C1과 C2가 모두 되는가.

**답.** 둘 다 된다. sid에서는 번역 없는 경로(identity 도메인과 uio)와 PAL 경로 모두에서 C1과 C2가 64 KiB와 4 KiB 전송에서 데이터 일치로 끝났다. 매핑하지 않은 IOVA로 보낸 요청은 DMAR fault로 막혔다.

**이유.** C2의 성패는 번역 유무가 아니라 플랫폼이 장치 간 읽기를 전달하는지에 달려 있다. 같은 PAL 커널, 같은 NVIDIA 이식본, 같은 시험 도구로 sid에서는 C2가 성공했으므로 PAL과 iommufd 경로는 C2를 막지 않는다. 개발 PC에서는 C2 한 번 뒤에 NVMe와 그 루트 포트(00:01.1)에만 UR 수신 비트가 서고 GPU와 GPU 쪽 루트 포트(00:01.0)에는 아무 비트도 서지 않았다(§6.1). 요청이 GPU 쪽 루트 포트에 도달하기 전에 루트 콤플렉스가 UR로 거부한 것이다. 클라이언트 루트 콤플렉스가 루트 포트 사이의 장치 간 읽기를 지원하지 않는다는 해석은 이 관측과 맞지만, Intel 문서로는 확인하지 않았다.

**성립 조건.** 결과는 sid의 소켓 0 안에서 GPU(루트 포트 30:02.0, 호스트 브리지 30)와 NVMe(호스트 브리지 4a, 루트 포트 4a:02.0 아래 Microchip 스위치 하위 포트 4c:01.0) 사이의 경로, VT-d 번역 켬, vfio-pci cdev와 iommufd, NVIDIA 580.178.04 이식본, 1 GiB 단일 구간 CUDA 버퍼, 4 KiB와 64 KiB 전송에 대한 것이다. sid에는 GPU와 같은 호스트 브리지 아래 NVMe가 없어 같은 호스트 브리지 안의 경로는 시험할 수 없었다.

**측정값.**

| 단계 | 시험 | 개발 PC | sid |
|---|---|---|---|
| A0 | 배포 커널 iommufd가 NVIDIA dma-buf를 거부 | 미시험 | `FAILED errno=95` |
| A1 | 번역 없이 C1 (NVMe→GPU) | MATCH | MATCH (64K, 4K) |
| A1 | 번역 없이 C2 (GPU→NVMe) | 실패 `sc=0x4` | MATCH (64K, 4K) |
| A2 | CPU의 BAR1 읽기 | MATCH | MATCH |
| C0 | PAL 매핑 | OK, 2 MiB x 512 | OK, `iova=0x200000 length=0x40000000` |
| C1 | 번역된 NVMe→GPU | MATCH | MATCH (64K, 4K, identity IOVA) |
| C2 | 번역된 GPU→NVMe | 실패 `sc=0x4` | MATCH (64K, 4K, identity IOVA) |
| D | 미매핑 IOVA에서 읽기 | `sc=0x4` + DMAR Read fault | `sc=0x4` + DMAR Read fault |

**의미.** 업스트림 PAL 경로(`IOMMU_IOAS_MAP_FILE`과 dma-buf mapping type)는 Xeon 호스트에서 본 팀의 두 I/O 방향을 모두 처리한다. 자체 모듈 `iommu_map_pa`가 맡던 GPU 메모리 매핑을 PAL 경로로 옮겨도 기능은 유지된다는 근거가 생겼다. 다만 이 결론은 데이터 일치만 확인한 것이고 대역폭과 지연은 측정하지 않았다.

**바로잡은 이전 기록.** 시험 도구 `pal_nvme.c`가 CC 레지스터의 IOSQES와 IOCQES 값을 서로 바꿔 쓰고 있었다. 개발 PC 결과(results-2026-10-13.md)도 이 버그가 있는 도구로 측정했다. 2026-10-15에 개발 PC에서 고친 도구와 버그가 있는 도구로 번역 없는 C1, C2를 나란히 실행했고, 두 도구 모두 C1 MATCH, C2 `sc=0x4`로 같았다(§6.1). 개발 PC의 C2 실패는 이 버그 때문이 아니다. sid 실행 중 처음 작성한 보고서는 개발 PC 실패의 원인을 "대조로 확인"했다고 썼으나 이 문서는 추정으로 낮췄다.

**확인하지 못한 것.** 개발 PC 루트 콤플렉스가 장치 간 읽기를 거부하는 것이 설계상 제약인지 설정으로 바꿀 수 있는지는 Intel 문서로 확인하지 못했다. 고친 도구로 다시 측정한 것은 번역 없는 C1, C2뿐이고, PAL 커널에서의 C1, C2, D는 다시 측정하지 않았다. C2의 대역폭과 지연, 소켓 간(UPI) 경로, exporter가 attach 시 자체 P2P 판정을 하는지도 확인하지 않았다. 각 항목의 다음 단계는 §9에 있다.

**반영한 변경.** `src/pal_nvme.c`의 CC 값을 고쳤고, 개발 PC 재측정 결과를 §6.1에 넣었다. sid에 남은 PAL 커널 파일과 `/etc/default/grub`의 `GRUB_DEFAULT` 고정은 §8에 적었다.

## 1. 원리와 예상 결과

NVMe 명령의 방향과 PCIe 트랜잭션의 종류는 반대로 대응한다. NVMe 읽기 명령은 장치가 대상 메모리에 쓰는 posted write를 만들고, NVMe 쓰기 명령은 장치가 소스 메모리를 읽는 non-posted read를 만든다. posted write는 완료(completion)가 없어서 라우팅에 실패해도 장치가 알 수 없다. non-posted read는 완료가 돌아와야 하므로 라우팅에 실패하면 UR이나 CA 완료가 돌아오고, NVMe는 이를 Data Transfer Error(`sc=0x4`)로 보고한다. 그래서 플랫폼이 장치 간 전달을 허용하는지는 C2가 가른다.

이 원리에서 나오는 예상은 다음과 같다. 가정 행은 관측 전의 예상이다.

| 조건 | C1 (posted write) | C2 (non-posted read) | 근거 |
|---|---|---|---|
| 플랫폼이 장치 간 읽기와 쓰기를 모두 전달 (가정) | MATCH | MATCH | |
| 플랫폼이 장치 간 쓰기만 전달 (가정) | MATCH | `sc=0x4` | 개발 PC 관측과 같은 모양 |
| 매핑하지 않은 IOVA | 명령 OK, DMAR Write fault | `sc=0x4`, DMAR Read fault | VT-d가 요청을 막고 posted write는 완료가 없다 |

커널 `drivers/pci/p2pdma.c`의 허용 목록에는 sid의 호스트 브리지 `8086:09a2`가 플래그 0으로 들어 있고 개발 PC의 `8086:a700`은 없다. 플래그 0은 다른 호스트 브리지 사이의 P2P도 허용한다는 뜻이다(`host_bridge_whitelist()`가 두 브리지가 다르면 각각을 같은 브리지 조건 없이 검사한다). 다만 이 시험의 경로(PAL 매핑과 `iommu_map_pa`)는 p2pdma 판정을 거치지 않으므로, 허용 목록은 시험 결과를 정하지 않고 플랫폼 특성의 간접 근거일 뿐이다.

### 2.2 GPU와 NVMe 사이의 경로

GPU는 호스트 브리지 30의 루트 포트 `30:02.0` 바로 아래에 있고, 이 호스트 브리지 아래에는 NVMe가 없다. 시험 NVMe는 호스트 브리지 4a의 루트 포트 `4a:02.0` 아래 Microchip PCIe 스위치(`11f8:4000`, 상위 포트 `4b:00.0`, 하위 포트 `4c:01.0`)에 붙어 있다. 30과 4a는 모두 소켓 0의 IIO 스택이다. 따라서 C2의 읽기 요청은 스위치를 올라가 루트 포트 4a:02.0에 들어간 뒤 소켓 0의 메시를 거쳐 루트 포트 30:02.0으로 나가야 한다.

ACS 설정은 이 경로를 바꾸지 않는다. 스위치 하위 포트 `4c:01.0`은 `ReqRedir+ CmpltRedir+ UpstreamFwd+`이므로 장치 간 요청을 스위치 안에서 처리하지 않고 위로 보낸다. 루트 포트 `30:02.0`과 `4c:01.0` 모두 `TransBlk-`다. 루트 포트 `4a:02.0`의 ACS 값은 수집하지 않았다.

## 3. 절차

매뉴얼의 단계를 그대로 따랐고, 각 단계의 명령과 출력은 `sid-raw/run-scripts/`와 `sid-raw/logs/`에 있다.

1. 사전 점검(읽기 전용): `precheck.txt`, `probe2.txt` ~ `probe6.txt`
2. 단계 A: 배포 커널에서 A0(MAP_FILE 거부)을 확인하고, NVMe를 identity 도메인과 uio_pci_generic에 묶어 번역 없이 C1, C2, A2를 실행했다(`stageA.txt`). 단계 A를 먼저 한 이유는 커널을 바꾸기 전에 플랫폼이 장치 간 읽기를 전달하는지부터 가리기 위해서다.
3. 단계 B: PAL 커널, NVIDIA 이식본, upcie 이식본을 빌드해 설치했다(`stageB-*.txt`).
4. 단계 C: PAL 커널로 한 번 부팅해 vfio-pci cdev로 C0, C1, C2, D, D2를 64 KiB, 4 KiB, identity IOVA로 반복하고 PTE를 읽었다(`stageC.txt`).
5. 복구: NVMe를 nvme 드라이버로 되돌리고 기본 커널로 재부팅했다(`stage7-*.txt`).

## 4. 결과

### 4.1 단계 A: 번역 없는 경로

```
IOMMU_IOAS_MAP_FILE: FAILED errno=95 (Operation not supported)
dmabuf_import: 16384 entries, first pa 0x20a031e00000, contiguous 1024 MiB
uio: 0000:4e:00.0 bar0 via sysfs, host pa 0x225fc00000, gpu pa 0x20a031e00000 (no translation)
C1 compare: MATCH (65536 bytes)
C2 compare: MATCH (65536 bytes)
CPU read through BAR1: MATCH
```

4 KiB 전송에서도 C1과 C2가 MATCH였고, dmesg에 DMAR과 AER 기록은 없었다. 이 결과는 sid 플랫폼이 소켓 0 안의 다른 호스트 브리지 사이에서 장치 간 읽기를 전달한다는 것을 보인다. 배포 커널의 iommufd는 NVIDIA dma-buf를 `EOPNOTSUPP`로 거부했으므로, 단계 C의 매핑 성공은 PAL 커널 덕분이다.

### 4.2 단계 C: PAL 경로

```
IOMMU_IOAS_MAP_FILE: OK iova=0x200000 length=0x40000000
gpu: dma-buf fd 34 (1024 MiB) mapped at iova 0x400000
C1 compare: MATCH (65536 bytes)
C2 compare: MATCH (65536 bytes)
D write LBA from unmapped iova (device read): status sct=0x0 sc=0x4
D2 read LBA0 into unmapped iova (device write, posted): OK
result: PASS (0 failure(s))
```

4 KiB 전송과 identity IOVA(GPU를 BAR1 물리주소 `0x20a031e00000`과 같은 IOVA에 매핑)에서도 C1과 C2가 MATCH였다. C2의 IOVA `0x400000`은 BAR1 물리주소와 다르므로, NVMe의 읽기 요청은 VT-d 번역을 거쳐 GPU에 도달했다. 이 결과가 PoC의 핵심이다.

D와 D2 직후 dmesg에는 다음 두 fault가 남았다.

```
DMAR: [DMA Write NO_PASID] Request device [4e:00.0] fault addr 0x80400000 [fault reason 0x05] PTE Write access is not set
DMAR: [DMA Read NO_PASID] Request device [4e:00.0] fault addr 0x80400000 [fault reason 0x06] PTE Read access is not set
```

두 fault는 §1의 예상과 같고, 개발 PC 로그(`run-2026-10-13.log`, `dmesg-2026-10-13.log`)에도 같은 모양이 있다. D(읽기)는 VT-d가 막아 오류 완료가 돌아왔고 NVMe가 `sc=0x4`로 보고했다. D2(posted write)는 VT-d가 막았지만 완료가 없으므로 NVMe는 명령을 성공으로 끝냈다. 즉 매핑이 사라진 IOVA로 NVMe 읽기 명령을 보내면 데이터는 버려지고 명령은 성공으로 보인다. 매핑 수명 관리에서 unmap과 진행 중인 명령의 순서를 지켜야 하는 이유가 여기에 있다.

### 4.3 PTE

`pal_probe --hold`로 매핑을 유지한 채 VT-d debugfs를 읽었다.

```
0x0000000000200 |	0x0000000000000000	0x00000001434d7003	0x00000001b1072003	0x000020a031e00883
0x0000000000400 |	0x0000000000000000	0x00000001434d7003	0x00000001b1072003	0x000020a032000883
entries: 514
```

하위 비트 `0x883`은 R, W, PS(2 MiB 페이지), SNP(bit 11)다. `entries: 514`는 `pte-dump.sh`가 `wc -l`로 센 값이라 머리글 두 줄이 들어 있고, 실제 엔트리는 512개(1 GiB / 2 MiB)다. 개발 PC와 같은 모양이다. SNP가 켜진 PTE로 C2가 성공했으므로, 개발 PC에서 SNP를 끄고도 실패한 결과와 함께 SNP는 C2 실패와 무관하다.

| PAL 경로 C1, C2 | 단계 A가 되면 둘 다 MATCH | MATCH | PAL 경로가 두 방향을 처리한다 |
| D | `sc=0x4` + Read fault | 같음 | 번역과 보호가 적용된다 |
| D2 | 명령 OK + Write fault | 같음 | posted write의 실패는 장치에 보이지 않는다 |
| PTE | 2 MiB, SNP 켜짐 | 같음 | SNP는 C2와 무관하다 |

측정으로 확인한 것은 둘이다. sid에서 PAL 경로가 양방향 DMA를 처리한다. 개발 PC에서는 NVMe의 읽기 요청이 GPU 쪽 루트 포트에 도달하기 전에 UR로 거부된다(§6.1). 따라서 GPU가 요청을 거부했을 가능성은 배제된다. 남은 추정은 이 거부가 클라이언트 루트 콤플렉스의 설계상 제약이라는 것이다.

## 6. 시험 도구 결함

단계 A의 첫 실행은 C1에 도달하기 전에 `create io cq failed: 0x102`로 끝났다. `0x102`는 Invalid Queue Size다. 원인은 `pal_nvme.c:411`이 CC 레지스터를 `(6 << 20) | (4 << 16) | 1`(0x00640001)로 쓴 것이다. 커널 `include/linux/nvme.h`에서 IOSQES의 시프트는 16, IOCQES의 시프트는 20이므로 이 값은 IOSQES=4, IOCQES=6으로 주석의 의도(IOSQES=6, IOCQES=4)와 반대다. admin 큐의 엔트리 크기는 CC와 무관하므로 Identify까지는 성공했고, sid의 드라이브는 I/O CQ 생성에서 이 값을 검사해 거부했다. 운영자 승인 후 `(6 << 16) | (4 << 20) | 1`로 고쳤다(`sid-raw/raw/pal_nvme-cc-fix.diff`). 이 커밋에서 `src/pal_nvme.c`도 같이 고쳤다.

개발 PC 결과도 이 버그가 있는 도구로 측정했다. 개발 PC 드라이브는 I/O 큐 생성을 허용했고, 같은 실행에서 호스트 메모리를 소스로 한 쓰기 명령과 C1이 성공했다. 따라서 드라이브가 CC 값을 쓰지 않고 표준 크기로 동작했다고 보았고, §6.1의 재측정으로 이를 확인했다.

### 6.1 개발 PC 재측정

2026-10-15에 개발 PC(커널 6.8.12-dmabuf, `intel_iommu=on`)에서 예비 NVMe를 identity 도메인과 uio_pci_generic에 묶고, 고친 `pal_nvme`와 버그가 있는 `pal_nvme.ccbug`로 번역 없는 C1, C2를 64 KiB와 4 KiB로 실행했다. 덮어쓴 LBA는 이전 시험과 같은 0 ~ 383이다. 네 번 모두 C1은 MATCH, C2는 `sct=0x0 sc=0x4`로 같았다. 이 결과는 CC 버그가 C2 실패와 무관함을 보인다.

이어서 루트 포트 두 개, GPU, NVMe의 Status와 DevSta 오류 비트를 지운 뒤 고친 도구로 C2를 한 번 실행했다.

| 장치 | 지운 뒤 | C2 한 번 뒤 |
|---|---|---|
| 00:01.0 (GPU 쪽 루트 포트) | 모두 - | 모두 - |
| 00:01.1 (NVMe 쪽 루트 포트) | 모두 - | `<MAbort+` |
| 01:00.0 (GPU) | 모두 - | 모두 - |
| 02:00.0 (NVMe) | 모두 - | `<MAbort+` |

`<MAbort+`는 Received Master Abort, 즉 UR 완료를 받았다는 뜻이다. GPU와 GPU 쪽 루트 포트에는 아무 비트도 서지 않았으므로 NVMe의 읽기 요청은 GPU 쪽 루트 포트에 도달하지 않았고, 루트 콤플렉스가 NVMe 쪽에서 UR로 끝냈다. 원본 출력은 `devpc-raw/run-2026-10-15-ccfix-ab.log`에 있다.

## 7. 매뉴얼과의 차이

| 항목 | 매뉴얼 | 실제 | 이유 |
|---|---|---|---|
| 접속 | `ssh root@sid` | `ssh jaeyoon@sid` 후 sudo | sid에서 root 키 인증이 되지 않았다 |
| CUDA | 3인자 `cuCtxCreate` | `gcc -include sid-cuda13-compat.h` | CUDA 13.3은 `cuCtxCreate`를 4인자 `cuCtxCreate_v4`로 바꾼다. shim은 `ctxCreateParams`에 NULL을 넘겨 소스를 고치지 않고 빌드했다 |
| 빌드 패키지 | flex, bison, pahole, libcap-dev | 추가로 libdw-dev | 커널 7.0-rc1의 `scripts/gendwarfksyms`가 `dwarf.h`를 요구한다 |
| 커널 소스 | 공개 git clone | GitHub PAT의 Basic 인증으로 clone | sid의 프록시가 큰 저장소의 ref 광고를 전달하지 못했고 codeload와 archive는 429를 돌려주었다 |
| initramfs의 dm 검사 | `dm-mod`가 없으면 멈춤 | 통과로 판단 | PAL 커널은 `CONFIG_BLK_DEV_DM=y`로 dm을 내장하므로 `dm-mod.ko`가 없다. 새 initrd에 `lvm`이 들어 있음을 확인했다 |
| GRUB 기본 항목 | 바꾸지 않음 | `GRUB_DEFAULT`를 `7.0.0-38-generic`으로 고정 | 원래 값 `0`이면 `update-grub` 뒤 버전이 가장 높은 PAL 커널이 기본이 된다 |
| 한 번만 부팅 | `grub-reboot` | `grub-reboot` 후 부팅해서 `next_entry` 수동 해제 | grubenv가 LVM 위에 있어 GRUB이 부팅 중에 `next_entry`를 지우지 못한다. 원격 콘솔이 없어 PAL 커널 부팅 실패 시 복구할 수 없다는 위험을 운영자에게 보고하고 승인받았다 |

## 8. 원상 복구 상태

- 시험 장치 `4e:00.0`은 nvme 드라이버와 DMA-FQ 도메인으로 돌아왔고 `/dev/nvme2n1`이 있다. hugepage는 0이다.
- 기본 커널 `7.0.0-38-generic`으로 재부팅했고 `nvidia-smi`는 정상이며 grubenv는 비어 있다.
- `/mnt/datasets`는 시험 전과 같이 마운트되지 않은 상태다. 데이터셋 장치 `4d:00.0`에는 접근하지 않았다.
- 남아 있는 변경이 둘 있다. 첫째, PAL 커널 파일(`/boot/*-rc1-pal+`, `/lib/modules/7.0.0-rc1-pal+`)은 운영자 결정으로 남겨 두었다. 둘째, `/etc/default/grub`의 `GRUB_DEFAULT`는 원래 `0`이었는데 지금도 `"Advanced options for Ubuntu>Ubuntu, with Linux 7.0.0-38-generic"`으로 고정되어 있다. 원본은 `sid-raw/sid-logs/grub.default.orig`에 있다. PAL 커널 파일을 지울 때 이 값도 되돌리고 `update-grub`을 실행해야 한다.
- 시험 전 실행 중이던 커널은 34-generic이었고 기본 항목은 38-generic이었다. 복구는 운영자 선택에 따라 38-generic으로 했다.
