# PAL PoC 1차 결과: CUDA dma-buf의 iommufd 매핑과 NVMe DMA

- 측정일: 2026-10-13
- 호스트: 개발 PC jaeyoon-pc (i9-14900K, VT-d, RTX PRO 4000 Blackwell at 0000:01:00.0, 예비 NVMe Samsung at 0000:02:00.0, GPU는 루트 포트 00:01.0, NVMe는 00:01.1)
- 커널: `7.0.0-rc1-pal+` (PAL 브랜치 c37cf2824740, `/data/linux-pal`), `intel_iommu=on`, passthrough 없음
- 드라이버: NVIDIA 580.178.04 오픈 모듈에 mapping type 이식과 PAL exporter를 더한 것(`/data/nvidia-580-pal`, 패치 `nvidia-580.178.04-pal-port.patch`), upcie-experimental 0.9.0 이식본(`/data/upcie-exp-pal`)
- 도구: `/data/aisio/pal-poc/pal_probe.c`, `pal_nvme.c`, 실행 로그 `run-2026-10-13.log`, 커널 로그 `dmesg-2026-10-13.log`

## 요약

**질문.** NVIDIA 드라이버에 PAL exporter를 더하면 CUDA가 내보낸 dma-buf fd를 업스트림 PAL 브랜치의 iommufd가 `IOMMU_IOAS_MAP_FILE`로 받아 NVMe의 IOMMU 도메인에 매핑하는가. 그 매핑으로 NVMe가 실제로 GPU 메모리에 DMA하는가.

**답.** 매핑은 된다. NVMe에서 GPU로 가는 DMA(NVMe 읽기 명령)는 번역된 IOVA로 동작하며 데이터가 일치한다. GPU에서 NVMe로 가는 DMA(NVMe 쓰기 명령, 장치가 GPU 메모리를 읽음)는 이 PC에서 `Data Transfer Error`로 실패하며, 이는 PAL 매핑의 문제가 아니라 장치가 GPU BAR1을 읽는 요청이 완료되지 않는 것이다.

**이유.** `IOMMU_IOAS_MAP_FILE`이 0을 돌려주고 IOVA(0x400000)가 BAR1 물리주소(0x480e800000)와 다른데도 NVMe 읽기 명령의 데이터가 `cuMemcpyDtoH`로 읽은 GPU 메모리 내용과 일치했으므로, NVMe의 DMA 쓰기가 VT-d 번역을 거쳐 GPU 메모리에 도달한 것이다. 매핑하지 않은 IOVA로 보낸 명령은 DMAR fault("PTE Read access is not set")와 명령 오류로 끝나 번역과 보호가 적용되고 있음을 보인다. 반면 NVMe 쓰기 명령은 GPU IOVA를 소스로 할 때 DMAR fault 없이 `sc=0x4`로 실패했고, IOVA를 BAR1 물리주소와 같게(identity) 매핑해도 같았다. fault가 없으므로 VT-d는 그 읽기 요청을 번역해 내보냈고, 오류 완료는 그 뒤(루트 콤플렉스 또는 GPU)에서 돌아온 것이다.

**성립 조건.** 결과는 이 PC(Intel 클라이언트 플랫폼, CPU 루트 포트 두 개 사이의 P2P), VT-d 번역 켬, vfio-pci cdev + iommufd, NVIDIA 580.178.04 이식본, 1 GiB 단일 구간 CUDA 버퍼에 대한 것이다. sid(Xeon)에서는 확인하지 않았다.

**측정값 표.**

| 실험 | 내용 | 결과 |
| --- | --- | --- |
| 프로브 | CUDA 1 GiB dma-buf를 `IOMMU_IOAS_MAP_FILE`에 (장치 없이) | OK, IOVA 0x200000 |
| 프로브 | 같은 것, NVMe를 HWPT로 붙인 뒤 | OK, IOVA 0x200000 |
| C1 | 호스트 패턴 → NVMe 쓰기(LBA 0) → NVMe 읽기 명령으로 GPU IOVA에 → `cuMemcpyDtoH` 대조, 4 KiB와 64 KiB | MATCH |
| C2 | `cuMemcpyHtoD` 패턴 → NVMe 쓰기 명령이 GPU IOVA에서 읽어 LBA 128에 → 호스트로 읽어 대조 | 쓰기 명령 `sct=0 sc=0x4`(Data Transfer Error), MISMATCH |
| C2 identity | GPU를 BAR1 물리주소 0x480e800000과 같은 IOVA에 고정 매핑하고 C2 반복 | 동일 실패 |
| D | 매핑하지 않은 IOVA 0x80400000에서 읽는 NVMe 쓰기 명령 | `sc=0x4`, dmesg에 DMAR Read fault |
| D2 | 같은 IOVA로 쓰는 NVMe 읽기 명령(posted) | 명령은 OK, dmesg에 DMAR Write fault |
| 회귀 | `dmabuf_import` misc 경로가 이식본 exporter에서 물리주소 목록을 받는가 | 64 KiB x 16384, 연속 1 GiB |

**의미.** PAL exporter 쪽은 약 150행으로 끝났고 iommufd 쪽은 브랜치를 그대로 쓴다. 본 팀의 주 사용 경로(NVMe에서 GPU로 읽기)는 PAL 경로로 동작한다. GPU에서 NVMe로 쓰는 방향은 이 PC에서 장치의 GPU 메모리 읽기가 실패하므로, 이것이 플랫폼 제약인지 번역 유무와 관련 있는지를 먼저 가려야 한다. 본 팀의 sid 벤치마크는 읽기 워크로드만 있었으므로 이 방향은 어느 호스트에서도 아직 측정된 적이 없다.

**확인하지 못한 것.** sid(Ice Lake-SP)에서 C2가 되는지는 이 문서를 쓸 때 확인하지 못했다. 2026-10-15에 sid에서 C2가 번역 유무와 관계없이 성공했다(results-2026-10-15.md). 이 문서의 측정에 쓴 `pal_nvme.c`에는 CC의 IOSQES와 IOCQES를 바꿔 쓰는 버그가 있었고, 2026-10-15에 고친 도구로 다시 실행해 C2 실패가 그 버그와 무관함을 확인했다. 같은 재측정에서 UR이 GPU 쪽 루트 포트에 도달하기 전에 루트 콤플렉스에서 나온 것도 확인했다(같은 문서 §6.1). 사용자가 이 PC에서 GPU→NVMe가 이전에 성공했다고 했는데, 그 경로가 실제 P2P 읽기였는지(GDS 호환 모드의 바운스 버퍼가 아니었는지)는 확인하지 못했다. C2 실패가 Intel 클라이언트 루트 콤플렉스의 P2P 읽기 미지원 때문이라는 것은 Intel 문서로 확인하지 않은 추정이다.

**반영한 변경.** 커널은 PAL 브랜치 그대로다. NVIDIA 모듈과 upcie-experimental 모듈에 이식 패치를 적용했고 DKMS 대신 수동 빌드로 설치했다.

## 1. 준비 과정에서 확인한 사실

- NVIDIA DKMS는 7.0 커널에서 `Makefile:18: /Kbuild: No such file or directory`로 소스 컴파일 전에 실패한다. 소스를 복사해 `make SYSSRC=/data/linux-pal NV_EXCLUDE_KERNEL_MODULES=nvidia-peermem modules`로 빌드하면 된다. `nvidia-peermem`은 OFED의 Module.symvers를 요구하므로 제외한다.
- 580.178.04와 610.43.02 모두 `nv-dmabuf.c`에서만 실패하며 원인은 같다. `struct dma_buf_attachment`에 `dev`가 없고, `dma_buf_ops`에 `map_dma_buf`가 없으며, importer 함수가 `dma_buf_sgt_*`로 바뀌었다.
- PAL 브랜치의 기반 커밋 41dae5ac5e15는 v7.1의 pin/revoke 정비를 이미 포함한다.
- upcie-experimental의 `dmabuf_import`도 같은 이유로 실패하며 다섯 곳을 고치면 된다. `iommu_map_pa`는 수정 없이 빌드된다.

## 2. 이식한 exporter의 동작

`match_mapping` 콜백이 discrete GPU(또는 FORCE_PCIE)에는 PAL을, 그다음에 plain SGT를 제시한다. iommufd는 PAL만 요청하므로 PAL이 선택되고, `map_phys`가 RM의 `memArea.pRanges[]`를 `dma_buf_phys_list`로 옮긴다. `dmabuf_import` 같은 SGT importer는 plain SGT로 매칭되며, importing device가 PCI이면 기존 토폴로지 검사를, misc 장치이면 검사 없이 통과한다. `dma_buf_pin()`은 NVIDIA에 pin 콜백이 없어 0이다.

## 3. 실험 절차

`pal_nvme`는 vfio cdev 장치를 iommufd에 묶고 HWPT를 만들어 붙인 뒤, 호스트 메모리 2 MiB를 `IOMMU_IOAS_MAP`으로, CUDA 버퍼 1 GiB를 `IOMMU_IOAS_MAP_FILE`로 같은 IOAS에 매핑한다. BAR0를 mmap해 관리 큐와 I/O 큐 쌍 하나를 세우고 Identify Namespace로 LBA 크기(512 B)를 읽는다. 전송은 4 KiB(PRP1만)와 64 KiB(PRP 리스트)로 했다. 쓰기는 예비 NVMe의 LBA 0과 128에 한다. 이 선택은 본 팀의 이전 테스트와 같다.

NVMe 읽기 명령은 장치가 메모리에 쓰는 것(posted write)이고 NVMe 쓰기 명령은 장치가 메모리를 읽는 것(non-posted read)이다. 실험 D를 쓰기 명령으로 한 이유는 posted write는 IOMMU가 막아도 장치에 오류가 돌아오지 않기 때문이다.

## 4. 결과 해석

| 항목 | 예상 | 측정 |
| --- | --- | --- |
| `IOMMU_IOAS_MAP_FILE` 반환 | 0 | 0 |
| NVMe → GPU 데이터 | 일치 | 일치(4 KiB, 64 KiB) |
| 미매핑 IOVA 읽기 | 오류 상태 + DMAR fault | `sc=0x4` + "PTE Read access is not set" |
| 미매핑 IOVA 쓰기 | 명령 OK + DMAR fault | OK + "PTE Write access is not set" |
| GPU → NVMe 데이터 | 일치 | `sc=0x4`, DMAR fault 없음 |

C2의 해석은 추론이다. VT-d가 fault를 기록하지 않았으므로 요청은 번역되어 GPU를 향해 전달되었고, Data Transfer Error는 PCIe 완료가 UR 또는 CA로 돌아왔다는 뜻이다. identity 매핑에서도 같았으므로 주소 값 때문이 아니다. 후보는 둘이다. 첫째, Intel 클라이언트 루트 콤플렉스가 루트 포트 사이의 P2P 읽기를 지원하지 않는다(쓰기만 지원). 둘째, VT-d가 번역한 peer 읽기(SNP 비트가 켜진 vfio 도메인 PTE)를 루트 콤플렉스가 처리하지 못한다. 번역 없는 환경에서의 같은 실험이 둘을 가른다.

## 5. 추가 확인: selftest, PTE, SNP 비트

**selftest.** PAL 브랜치의 iommufd selftest는 처음에 241개 중 22개가 실패했으나, 실패는 모두 `MAP_HUGETLB` mmap 실패였다. hugepage 64개를 잠시 예약하고 다시 실행하자 pass 236, fail 0, skip 5였다. dma-buf 관련 테스트(`dmabuf_simple`, `dmabuf_multi_page`, `dmabuf_revoke`)는 두 번 모두 통과했다.

**PTE.** PAL 매핑을 유지한 채 VT-d debugfs(`/sys/kernel/debug/iommu/intel/0000:02:00.0/domain_translation_struct`)를 읽었다. GPU 구간은 PDE 레벨 엔트리 512개이고 값은 `0x000000480e800883`부터 2 MiB씩 증가한다. 하위 비트 0x883은 R(비트 0), W(비트 1), PS(비트 7, 2 MiB 페이지), SNP(비트 11)다. 따라서 PAL 매핑도 기존 측정과 같이 2 MiB x 512로 들어가며, 모든 엔트리에 SNP가 켜져 있다.

**SNP의 출처.** iommufd는 MMIO 배치에서 `IOMMU_CACHE`를 빼고 `IOMMU_MMIO`를 붙인다(`pages.c` 521~522행). 그러나 generic_pt의 VT-d second-stage 형식은 도메인에 `PT_FEAT_VTDSS_FORCE_COHERENCE`가 켜지면 `iommu_prot`와 관계없이 SNP를 세운다(`drivers/iommu/generic_pt/fmt/vtdss.h`의 `vtdss_pt_iommu_set_prot()`). iommufd HWPT는 장치가 지원하면 cache coherency를 강제하므로 이 기능이 켜진다. 이 PC의 dmar1은 ecap 0xf050da로 Snoop Control(비트 7)을 지원한다.

**가설.** NVMe가 GPU BAR1을 읽는 요청이 snoop 속성으로 번역되어 루트 콤플렉스에 전달되고, 루트 콤플렉스가 그 peer 읽기를 오류로 완료한다고 추정한다. GPU에 쓰는 방향은 posted write라 snoop과 무관하게 전달된다. 사용자는 이 PC에서 GPU→NVMe 방향이 이전에 성공했다고 확인했는데, 그 경로는 SNP를 강제하지 않는 DMA-FQ 기본 도메인을 쓴다. 이 세 사실은 가설과 맞지만 아직 추론이다.

**검증 준비.** `vtdss.h`에서 `IOMMU_MMIO` 매핑에는 SNP를 세우지 않도록 고친 커널을 빌드했다(패치 `kernel-vtdss-mmio-nosnp.patch`, 6행 추가 1행 삭제). 커널 내장 코드만 바뀌어 모듈과 initramfs는 그대로 쓴다. 설치는 `install-snp-kernel.sh`(root)로 하고, 재부팅 후 C2가 MATCH가 되면 가설이 확인된다.

## 6. 원인 확인: 플랫폼의 P2P 읽기 미지원

**SNP 가설 기각.** 2026-10-14에 MMIO PTE에서 SNP를 빼는 커널(#2)로 부팅해 PTE가 `0x000000480f600083`(SNP 없음)인 것을 debugfs로 확인한 뒤 C2를 다시 돌렸다. 4 KiB, 64 KiB, identity IOVA 모두 같은 `sc=0x4`로 실패했다. SNP 비트는 원인이 아니다.

**번역 제거.** NVMe의 IOMMU 그룹을 identity(번역 없음)로 바꾸고 uio_pci_generic에 묶은 뒤, `pal_nvme --uio`로 같은 C1, C2를 물리주소로 보냈다. C1은 일치했고 C2는 같은 `sc=0x4`로 실패했다. 번역이 없어도 실패하므로 IOMMU, iommufd, PAL과는 무관하다.

**BAR1 자체.** 같은 CUDA 버퍼를 CPU가 GPU의 `resource1`(BAR1) mmap으로 읽으면 64 KiB가 모두 일치했다. BAR1 주소와 내용은 올바르다.

**결론.** 이 PC에서는 NVMe가 GPU BAR1을 읽는 장치 간 읽기(non-posted)가 오류 완료로 끝나고, 장치 간 쓰기(posted)만 된다. 호스트 브리지 8086:a700(Raptor Lake 클라이언트)은 커널 `drivers/pci/p2pdma.c`의 P2P 허용 목록에 없다. 목록에 있는 Intel 항목은 Xeon 계열이며 sid의 Ice Lake-SP 호스트 브리지(0x09a2)는 목록에 있다. Intel 클라이언트 루트 콤플렉스가 루트 포트 사이의 P2P 읽기를 지원하지 않는다는 해석과 맞지만, 이 해석은 Intel 문서로 확인하지 않은 추정이다.

**바로잡은 이전 기록.**

| 이전 서술 | 바로잡은 내용 | 경위 |
| --- | --- | --- |
| C2 실패는 SNP 비트 때문으로 추정한다(§5) | SNP를 끄고도 실패하고, 번역을 끄고도 실패한다. 원인은 플랫폼의 P2P 읽기다 | PTE에서 SNP를 발견하고 DMA-FQ 경로의 성공 기록과 맞춰 본 정황 추론이었다 |
